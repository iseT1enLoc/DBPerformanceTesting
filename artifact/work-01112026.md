## 1. Project Simplification — Removed Spring Boot

The original project used Spring Boot as a full benchmark framework (`CommandLineRunner`, `@ConfigurationProperties`, `HdrHistogram`, multi-threaded `Worker` pool, `ResultWriter` CSV output). This was replaced with a single plain-Java `Main.java`.

**Deleted classes:**

| Package | Class | Reason |
|---------|-------|--------|
| `bench` | `BenchmarkRunner`, `Worker`, `Operation`, `RunResult` | Replaced by `Main.java` |
| `config` | `BenchmarkProperties`, `ClientConfig` | Spring wiring no longer needed |
| `workload` | `DataSet`, `PayloadSizer`, `TableSetup`, `Scenario` | Not needed for simple benchmark |
| `report` | `ResultWriter` | Output goes directly to stdout |

**Kept unchanged:**

| Package | Class |
|---------|-------|
| `client` | `NoSqlClient`, `KvClientImpl`, `SdkClientImpl`, `Sql` |
| `model` | `Order`, `ConsistencyLevel`, `DurabilityLevel` |
| `workload` | `OrderCsvReader` |

**`pom.xml` changes:** removed `spring-boot-starter`, `spring-boot-starter-test`, `HdrHistogram`, `maven-failsafe-plugin`. Kept `spring-boot-starter-parent` (manages Java 17 compiler config) and `spring-boot-maven-plugin` (fat jar). Set explicit `mainClass`.

## 2. Connection Issue — Docker Hostname Not Resolvable

### Problem

kvclient connected to `localhost:5100` (bootstrap), but Oracle KVLite advertises its storage node hostname as `kvlite` (the Docker container hostname set in `docker-compose.yml`). kvclient then tried to resolve `kvlite` and failed:

```
Caused by: java.net.UnknownHostException: kvlite
```

### Fix

Added `172.18.0.3 kvlite` to `/etc/hosts` (using the container's actual Docker bridge IP, not `127.0.0.1` — the latter would fail because port 5000 is not mapped to the host, only 5100 is, but `172.18.0.3:5000` reaches the container directly):

```bash
echo "172.18.0.3 kvlite" | sudo tee -a /etc/hosts
```

### Problem 2 — SDK wrong port

`Main.java` initially hardcoded `localhost:8090` for the SDK proxy, but `docker-compose.yml` maps the proxy to `8180`. Fixed by updating the constant.

## 3. Connection Retry with Exponential Backoff

Added a generic `retry()` helper so the program waits for the store to finish booting instead of failing immediately:

```java
private static <T> T retry(String name, Callable<T> action) throws Exception {
    long delay = INITIAL_DELAY; // 1s
    for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {  // up to 5 attempts
        try { return action.call(); }
        catch (Exception e) {
            if (attempt == MAX_ATTEMPTS) throw e;
            Thread.sleep(delay);
            delay *= 2; // exponential: 1s → 2s → 4s → 8s
        }
    }
}
```

## 4. Added `put_batch` and `put_bulk` Benchmarks

### `put_batch`

Sends all orders for one customer as a single atomic batch (same shard key). Added to both clients.

Orders grouped by customer:
```java
List<List<Order>> batches = new ArrayList<>(groupByCustomer(orders).values());
```

### `put_bulk`

kvclient-only cross-shard parallel write via `TableAPI.put(List<EntryStream<Row>>, BulkWriteOptions)`.

Fixed-size cross-shard partitions:
```java
List<List<Order>> bulkBatches = partition(orders, BULK_BATCH); // BULK_BATCH = 1000
```

SDK prints `n/a` for `put_bulk` since it has no equivalent API.

### Bug fix — `NullPointerException` in `putBulk`

`tableAPI.put()` internally calls `streams.contains(null)` to track exhausted streams. `List.of()` throws `NullPointerException` on `contains(null)` because it is null-hostile. Fixed by using a mutable `ArrayList`:

```java
// Before (crashes):
tableAPI.put(List.of(new OrderStream(t, orders)), opts);

// After (works):
List<EntryStream<Row>> streams = new ArrayList<>();
streams.add(new OrderStream(t, orders));
tableAPI.put(streams, opts);
```

## 5. Sequential vs `putBulk` Comparison

Added a dedicated section that inserts the same N records both ways and compares total time:

```
--- Insert 100000 records: sequential vs putBulk(batch=1000) [kvclient, 5 runs] ---
method                      rows/s      total ms       calls
------------------------------------------------------------
sequential (put_single)       5,026       19897.7     100,000
putBulk (batch=1000)        151,462         660.2         100
```

`putBulk` is ~30× faster because it reduces 100,000 blocking round-trips to 100 calls, with the driver processing batches in parallel across shards.
